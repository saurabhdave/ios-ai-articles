Opening

We’re all seeing the same thing: watchOS battery regressions that don’t show up until a real wrist, real motion, and a shaky network get involved. Meanwhile, package selection is getting smarter and the community is poking at Apple’s formats again, but none of that matters if your app quietly wakes the radio at 3%/hour. This week is about making your profiling repeatable and your conclusions defensible.

This Week's Big Story

Profiling watchOS Battery Drain with Instruments

Tiny inefficiencies drain Apple Watch batteries: extra renders, stray timers, and too many radio wakeups. The simulator hides these costs; only physical hardware shows the real story. If you want to stop guessing, you need reproducible on-device traces, disciplined signposts, and the courage to delete work your UI doesn’t need.

Swift Snippet of the Week

import Network actor Scenario { private let monitor = NWPathMonitor() func waitForOffline() async { monitor.start(queue: .global()) while monitor.currentPath.status != .unsatisfied { try? await Task.sleep(nanoseconds: 300_000_000) } } }

Use this to build deterministic “offline first” test lanes so your energy traces cleanly separate UI/CPU cost from network/radio overhead.
